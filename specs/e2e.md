# e2e

Problem: the repository's own use of git and CI (project branches and landings, CI segmentation by reach, goldens and scenarios gated by reach) has no measure over whole sequences. The previous repository's end-to-end tests were vacuous: they checked that git and GitHub work, spent hundreds of processes doing it, and left these decisions untested.

L1 Report only: a scenario prints numbers and asserts none of them. No required check runs it, and nothing blocks on a number; any target is the owner's to set.
L2 Blackbox: a scenario drives the production decisions through `ci::Cli::answer` alone, with an in-memory fake of `ci::ports::Ports` answering `cargo metadata`, `git` and `gh`. No network, no process, no real git or gh, no third-party service. It never tests that git or GitHub work.
L3 The world is the repository as it stands: the fake's `cargo metadata` is built from the workspace manifests on disk. Adding, removing or rewiring crates moves the numbers and never needs a scenario edit; a scenario that detail feature work forces to change is mis-scoped and goes back to the owner.
L4 Scenarios are designed with the owner before the work they measure. Agents implement them and optimise against their numbers; agents do not add scenarios.
L5 The event model is what `ci.yml` triggers: CI runs on every pull request and on pushes to main only. A scenario states the runs it counts in these terms.
D1 Harness: crate `e2e` at the repository root, a workspace member outside `default-members`, with one test target `tests/e2e` behind the feature `measure`, so plain `cargo test` and the required checks never build or run it. Workflow `e2e` runs it on pushes to main and by hand, and appends its report to the job summary. A report line is `e2e <scenario> <name>=<value>`.
D2 Scenario `reach`. Blackboxes: CI segmentation (`ci reach` for a pull request into a project branch, segmentation L1, D6). Inputs: every workspace crate, each changed alone by one source file. Numbers: `share`, the mean fraction of crates such a pull request builds, the tangle measure to lower; `misses`, crates the reverse-dependency closure of the manifests holds but `BUILD_SCOPE` omits; `extras`, the converse. Not vacuous: the expected set is computed by the scenario from the manifests, not by `reach`, and the observed set is the `BUILD_SCOPE` text the workflow feeds to cargo; a reach that selected everything, or dropped a dev-dependency edge, moves `extras` or `misses`. after: D1
D3 Scenario `landing`. Blackboxes: project branches and landings against direct pull requests into main, as `ci reach` scopes each run. Inputs: the crates in name order, cut into projects of four pull requests, one crate each. A project spends one run per pull request into its branch, one landing pull request into main and one push to main; the direct path spends a pull request into main and a push to main per change. Numbers: `runs` and `crate_builds` (the workspace counts in full for `--workspace`) and `mutant_crates`, per landed change, for each path. Not vacuous: the scopes come from the production decision on each run's event and base, so widening project pull requests, or narrowing pull requests into main, moves the numbers; it measures repeated CI spend, the problem the owner named. after: D2
D4 Scenario `golden-reach`. Blackboxes: goldens and new scenario files pass only within a pull request's reach (`ci labels`, test-tooling D6, D7). Inputs: every ordered pair of crates, a pull request changing a source file of the first and a golden of the second, then adding a scenario file under the second's `tests/e2e`, with no label. Numbers: `owner_share`, the fraction of pairs that need the owner's label, which is how often this rule reaches the owner; `disagreements`, verdicts that differ from whether the second crate lies in the closure of the first. Not vacuous: the expected verdict is the scenario's own closure, and the observed one is the exit code of the step the labels workflow runs. after: D1
Out: ratchets and landings refused for undisposed bugs, which this repository does not hold; merge queues, not built; whether real git and gh behave as the fake assumes, which is recording's job; timings, which belong to segmentation D5.
